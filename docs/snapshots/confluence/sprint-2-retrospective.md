## 2. What Didn't Go Well? 👎

What caused difficulties, delays, confusion, or unnecessary work?

| Issue | Impact on Sprint |
| --- | --- |
| Documented Communication | Struggled to understand where everyone else was in the sprint. Didn’t maintain an accurate shared understanding of project progress.  |
| Lack of documented high level architecture diagrams to inform implementation decisions | Code reviews more difficult between members because of lack of shared design understanding. Knowledge gap between two teams, i.e. Frontend team has limited understanding of backend architecture |
| We didn’t integrate the front and back ends.  | Technically we were meant to do the integration in this sprint but were set back. |
| Jumped into using Github without a plan or strategy.  | Not utilising GitHub to the fullest, making team communication suboptimal. Lucky we caught it now otherwise in future it will be very difficult to merge each other’s work.  |

---

## 3. What Should We Improve? 💡

What could we do differently next sprint?

* Prioritise monitoring of backlog tasks to maintain accountability and improve productivity
* Checking in with the client more often, making sure we’re both on the same page about our design. Ensuring the client has a good understanding of our product.
* Documentation of any work, meetings, and progress decisions being made.

### Proposed Changes

| Improvement | Expected Benefit |
| --- | --- |
| Use **GitHub Projects** to assign, manage, and monitor backlog tasks, including clearly identifying the team member responsible for each task. | Provides greater visibility of sprint progress and individual responsibilities, improving accountability and making it easier to identify incomplete or blocked tasks early. |
| Create and use separate slack channels for more frequent team updates, code reviews, questions, proposed changes/feedback on individual work | Enhance workflow, increase productivity of independent tasks and keep everyone in the know of what is going on. |
| Recording all meetings and having a transcript + summary notes of everything discussed. | Team members will be able to reference back to the meetings to clear up anything that was discussed.  |

## 4. Key Learnings

What did we learn during this sprint?

* We need to communicate better and it directly affects team progress
* Have more architectural diagrams for a full high level overview of our system.
* Client communication important for reviewing and confirming requirements

# **Retrospective summary:**

‌

Overall, this sprint was productive and we successfully progressed towards the product we set out to build. The team worked well independently and achieved the main scope we established for the sprint. However, we identified communication, documentation and coordination as areas that need improvement. In particular, the lack of a shared understanding of the overall architecture made code reviews and frontend/backend collaboration more difficult, and we were unable to complete the planned frontend/backend integration.

Going into the next sprint, our main focus will be on integration, stronger architectural documentation, and establishing a more structured team workflow. We will use GitHub Projects and a clearer GitHub workflow to improve accountability, while using Slack and documented meeting summaries to maintain a shared understanding of progress. We will also communicate with the client more frequently to validate our design decisions and ensure the product continues to meet their requirements.
